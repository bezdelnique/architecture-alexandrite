# Планирование: анализ, идентификация проблем и поиск решений


## Проанализируйте схему и описание системы.

Как основу для анализа использую жалобы пользователей системы

Жалобы клиентов
- Задержка сроков исполнения заказа онлайн-магазина
- Задержка сроков исполнения заказов созданных через API

Жалобы пользователей API, т.е. b2b партнеров
- Их клиенты не получили свои заказы

Жалобы операторов
- Задержки с отображением главной страницы MES



Вижу следующие возможные проблемы
- Взаимодействие CRM API - MES API происходит через очередь, возможна потеря сообщений
- Возможны расхождения при сохранении статуса в БД и созданием сообщения 
- Проблема с запросом на вывод последних заказов MES. Это можно решить оптимизацией запроса к БД или кешированием
- Возможна нехватка ресурсов. Веб-серверов: MES API, Shop API
- Возможна нехватка ресурсов. БД: MES DB, Shop DB 
- Возможна нехватка ресурсов. Очереди 


## Инициативы в порядке приоритета
- Кеширование запроса отображающего заказы на главной странице MES
- В части MES-очередь-CRM проверить наличие обработки ситуации делающей недопустимым расхождения изменения заказа в БД и отправки сообщения в очередь
- Внедрение мониторинга инфраструктуры: веб-серверов, БД, очереди
- Для мониторинга очереди: потерянные сообщения
- Внедрение мониторинга бизнес-метрик: время заказа в статусе, суммарное время заказа. Сделать алерты по порогам.
- Выделение партнерского API в отдельный контур: веб-сервер+БД

Работа по решению вопроса ресурсов будет зависеть от анализа инфраструктуры.

## Какой вы видите целевую архитектуру через полгода?

В ключе отказоустойчивости, т.е. нужно ли решать вопрос с производительностью БД и веб-серверов все зависит от фактической ситуации по нагрузке.

Выделение партнерского API в отдельный контур: веб-сервер+БД считаю целесообразным по причинам безопасности и отказоустойчивости.


> Если бы у вас была возможность выполнить только три пункта из списка инициатив в ближайшие полгода, что бы вы выбрали и почему?
Не обязательно добавлять в список только эпики. Вы можете включить в план как крупные изменения, так и локальные задачи.

- Кеширование запроса отображающего заказы на главной странице MES
- В части MES-очередь-CRM проверить наличие обработки ситуации делающей недопустимым расхождения изменения заказа в БД и отправки сообщения в очередь
- Внедрение мониторинга инфраструктуры: веб-серверов, БД, очереди. Методом мониторинга RED

Но пункт про мониторинг очередь выполняется легко.

Что касается кэширования запроса. У нас один истанс приложения и я бы делал кэширование на локальной памяти как быстрый фикс. При развитии инфраструктуры можно внедрить редис.
