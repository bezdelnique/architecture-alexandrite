# Мотивация
Мотивация схожа с той которую я описывал для трейсинга.

- Для ряда случаев вместо локального воспроизведения ошибок на машине разработчика, достаточно будет посмотреть логи.
- Грамотно и полно реализованное логирование позволяет искать странные и редкие ошибки в приложении и решать их в корне.
- Внедрение логирования позволит без потери контроля добавлять новые элементы инфраструктуры и интеграции

Метрики на которые повлияет логирование
- Время исправления ошибки при взаимодействии с инфраструктурой и внешними интеграциями
- Среднее время на устранение ошибок
- Возможно: сокращение времени релизов за счет ускорения диагностики ошибок-блокеров

Пункт про невозможность покрытия логами и трейсингом мне непонятна. Все API нужно покрыть логированием и трейсингом. nginx сервисов можно покрыть логированием во вторую очередь.

# Предлагаемое решение
Использовать буду стэк Grafana, Loki, Promtail.

Promtail - ставиться на каждый сервис откуда нужно собирать логи
Loki – БД для логов
Grafana – UI поиска по логам

Это стек предпочитаю ELK т.к. Grafana уже присутствует в технологическом ланшафте. Плюс Loki экономичнее в плане ресурсов чем ElasticSearch.

Поиск по логам в Loki это диапазон времени + метки.

Для логов nginx настройка формата логов не требуется. Метки Loki: приложение=nginx, сервер, уровень ошибки.

Формат логов приложения, произвольная строка в зависимости от приложения. Для java это будет. Метки Loki: приложение, сервер, уровень ошибки.

## Политика хранения логов
- Хранение логов по приложению 2 месяца
- Специальная настройка индекса для Loki не требуется

## Безопасность
- Логирование должно быть изолировано от внешнего контура. Доступ к UI должен быть только из частной сети компании. Нужно учесть необходимость конфигурации сети т.к. система находится в облаке.
- Доступ для сотрудников отдела разработки: бэкенд-программисты, тестировщики, девопс. Роли: developer, qa, devops.
- Доступ для сотрудников отдела поддержки. Роль: support.
