# Список данных, которые должны попадать в трейсинг
- Код приложения (например: mes_api)
- Код сервиса (например: create_order)
- Полезные данные (например: order_id, order_status)

# Мотивация
- Добавление трейсинга сократит время на диагностику проблем в которые вовлечено более одного сервиса.
- Для ряда случаев вместо локального воспроизведения ошибок на машине разработчика, достаточно будет посмотреть трейсинг.
- Внедрение трейсинга позволит с большей легкостью включать новые внешние зависимости не теряя контроля

Метрики на которые повлияет трейсинг
- Время исправления ошибки при межсервисном взаимодействии
- Снижение количества заказов которые выполняются слишком долго (возможно)
- Кол-во жалоб b2c пользователей на потерю заказов
- Кол-во жалоб b2b пользователей на проблемы с API
- Возможно: сокращение времени релизов за счет ускорения диагностики ошибок-блокеров

# Предлагаемое решение
В качестве инструмента я предлагаю OpenTelemetry+Jaeger. Моя идея в том чтобы фиксировать для заказа изменение его статуса. В системе два источника заказов: интернет-магазин и партнерский API.

## Статусы заказа интернет-магазина
```
INITIATED [онлайн-магазин] — пользователь завёл новый заказ или положил товары в пустую корзину.
FILE_UPLOADED [онлайн-магазин] — пользователь загрузил файл с 3D-моделью или создал его с помощью конструктора.
SUBMITTED [онлайн-магазин] — пользователь нажал на кнопку «Сделать заказ».
PRICE_CALCULATED [MES] — система посчитала стоимость заказа.
MANUFACTURING_APPROVED [CRM] — заказ подтверждён, его можно отдавать в производство.
MANUFACTURING_STARTED [MES] — оператор взял заказ в работу.
MANUFACTURING_COMPLETED [MES] — оператор выполнил заказ.
PACKAGING [MES] — оператор начал упаковывать заказ.
SHIPPED [MES] — заказ отправлен покупателю.
CLOSED [CRM] — заказ завершён. Он закрывается после получения сообщения от транспортной компании или вручную.
```

## Статусы заказа партнерского API
```
INITIATED [partner-api] — пользователь завёл новый заказ или положил товары в пустую корзину.
FILE_UPLOADED [partner-api] — пользователь загрузил файл с 3D-моделью или создал его с помощью конструктора.
SUBMITTED [partner-api] — пользователь нажал на кнопку «Сделать заказ».
PRICE_CALCULATED [MES] — система посчитала стоимость заказа.
MANUFACTURING_APPROVED [CRM] — заказ подтверждён, его можно отдавать в производство.
MANUFACTURING_STARTED [MES] — оператор взял заказ в работу.
MANUFACTURING_COMPLETED [MES] — оператор выполнил заказ.
PACKAGING [MES] — оператор начал упаковывать заказ.
SHIPPED [MES] — заказ отправлен покупателю.
CLOSED [CRM] — заказ завершён. Он закрывается после получения сообщения от транспортной компании или вручную.
```

Для систем онлайн-магазин, partner-api, MES, CRM нужно добавить отправку данных в трейсинг при изменении статуса заказа. При этом неважно происходят взаимодействия с другими частями системы или изменение заказа происходит в рамках одного сервиса.

## Компромиссы
В текущем случае не вижу компромиссов на которые мы должны пойти. Все компоненты системы являются либо внутренней разработкой. Система MES приобретена с возможностью вносить изменения в исходный код.

## Безопасность
- Трейсинг должен быть изолирован от внешнего контура. Доступ к UI должен быть только из частной сети компании. Нужно учесть необходимость конфигурации сети т.к. система находится в облаке.
- Доступ для сотрудников отдела разработки: бэкенд-программисты, тестировщики, девопс. Роли: developer, qa, devops.
- Доступ для сотрудников отдела поддержки. Роль: support.

# Предлагаемое решение
В качестве мониторинга и алертинга хочу использовать Prometheus+Grafana.

**Мониторинг перехода статусов с ссылкой на трейс**
* Организовать передачу данных в Prometheus из приложения используя OTel или импортом непосредственно из Jaeger: order_id, status_from, status_to
* Время есть, trace_id тоже
* На уровне Grafana Alerting проверять что для определенной пары duration([status_from, status_to]) > t, где t время в минутах допустимое для проведения в этом статусе. Отправлять уведомление с ссылкой на трейс в Jaeger.


**Мониторинг зависания заказа в определенном статусе**
* Подключить экспортер Postgresql к Prometheus
* На уровне Grafana Alerting проверять что есть заказы не в статусе CLOSED дольше t

Запрос на выборку зависших заказов примерно такой
```sql
SELECT
o.order_id,
o.creation_time as order_creation_time,
o.order_status_id,
os.creation_time as status_creation_time
FROM order o
JOIN order_status os ON o.order_id = os.order_id and o.order_status_id = os.order_status_id
WHERE o.order_status_id!=’CLOSED’ and (os.creation_time-os.creation_time) > t
```
